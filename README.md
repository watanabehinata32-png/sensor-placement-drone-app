# センサー配置と災害時ドローン巡回（sensor_app）

企業のお題「新緑県 広域観測網の最適化問題」の一段階目（センサーの配置）と二段階目（災害時のドローン巡回）を、
1 つの Web サイトで解くアプリです。計算は Python（FastAPI）、画面は HTML と JavaScript です。
ソルバーは Fixstars Amplify AE（トークンがないときだけ、確認用に手元のタブーサーチ）。

## 起動のしかた（Mac）

```bash
cd sensor_app
python3 -m pip install -r requirements.txt     # 最初の 1 回だけ
cp .env.example .env                            # 最初の 1 回だけ。.env を開いて AMPLIFY_TOKEN= の後ろにトークンを書く
python3 -m uvicorn server.main:app --port 8000
```

ブラウザで http://127.0.0.1:8000 を開きます。止めるときはターミナルで Ctrl + C。
画面右上に「ソルバー: Amplify AE」と出ていれば、トークンが読めています。

## 使い方

1. 最初に「一段階目から」か「二段階目から（厳密解の配置／保存した配置ファイル）」を選ぶ。
2. **① 配置**: 「QUBO で配置を計算」。結果は地図（種類ごとの色とカバー円）と市町村ごとの表に出る。
   「配置をファイルに保存」で placement.json に保存でき、あとで読み込める。
3. **② 被害**: 地図のクリックで通行止め（道路）と通信断（センサー）を切り替える。震源を置いてまとめてつくることもできる。
   最初はサンプルの地震（資料 p.6 の図から読み取ったもの）が入っている。車・バッテリー・QUBO の重みは「詳しい設定」。
4. 「ドローンの巡回を計算」→ **③ 結果**: 車ごとの走行ルート・ドローンの飛行・回復時刻と、車ごとの時刻表。
   地図の下の ▶ とスライダーで、車（道路の速さどおり）とドローン（🛸）の動きを再生できる（1・5・10 倍）。
   センサーは回復した時刻に赤から緑に変わり、左上に「○○分：回復 n 基」と車ごとの状態が出る。時刻表の横棒を押すとその時刻へ飛ぶ。
   「被害を変える」で ② に戻って解き直せる。① をやり直すと、設置しなくなったセンサーは通信断から外れる（知らせが出る）。

## 初期値と判定

- 一段階目: マス目 500 m・λ_cov 4・制限時間 5000 ミリ秒・罰則（1 地点 1 台、α・β）は重みなし（= 1）。
  前回の公開版（Render、GitHub の Optimal-Sensor-Placement-in-Two-Dimensions）と同じ。
  中央市のカバー率下限は元データの 100% から 95% に下げている。センサー性能表・市町村の必要値表は「詳しい設定」で変えられる。
- 判定はゆるみなし（カバー率が下限に少しでも届かなければ ✗）。前回の版にあった「0.1 ポイントまでおまけ」はやめた。
- 二段階目: Amplify の制限時間 3000 ミリ秒 × 最大 8 回（上限時刻 T を変えて解く）。最初の T は手早い答え（貪欲法）の終了時刻。

## フォルダの中身

| 場所 | 中身 |
|---|---|
| `server/main.py` | 計算の窓口（/api/...）。画面から条件を受け取り、core の計算を呼んで答えを返す |
| `server/settings.py` | .env からトークンを読む |
| `core/phase1.py` | 一段階目の QUBO（phase2_app/page_phase1.py の式をそのまま移したもの） |
| `core/preprocess.py` ほか | 二段階目の計算（phase2_app/core のコピー）。前処理 → 一体型 QUBO → T の二分探索 |
| `web/` | 画面（index.html・app.js・style.css）。地図は Leaflet（web/vendor に同梱） |
| `data/` | 配布データ・厳密解の配置・道路データ（phase2_roads_v2 のコピー。本データが来たら data/roads を差し替え） |

## 窓口（API）の一覧

| 窓口 | すること |
|---|---|
| GET `/api/map` | 地図データ（県・市町村・候補地点・道路・拠点・凡例の色）とサンプルの被害 |
| POST `/api/phase1/solve` | 一段階目を解く |
| POST `/api/phase1/check` | 読み込んだ配置のコストと達成状況 |
| GET `/api/phase1/exact` | 厳密解の配置（保存ファイルを読むだけ） |
| POST `/api/damage` | 震源から被害をつくる |
| POST `/api/preprocess` | ドローンで届かないセンサーの判定 |
| POST `/api/phase2/solve` → GET `/api/phase2/jobs/{番号}` | 二段階目を解く（受付番号で進み具合を問い合わせる） |

## わかっている課題

- 二段階目で、QUBO の答えだけでは全部のセンサーを回りきれないことがある（サンプルで 14 基中 8 基）。
  回りきれなかったセンサーは計算のあとに貪欲法で予定に付け足し、③ に ⚠ の注意を出す。
  直す案: QUBO の大きさ（車 × 枠 × 飛行）を減らす。

## まだ入れていないもの（後で）

- 厳密解で解く機能（どんな条件で比べるかを決めてから）
- アニメーションの「次の回復まで進む」「1 台だけ表示」

## 確認用の小さな道具（tools/）

- `python3 tools/check_phase2.py` … サンプルの地震で二段階目を 1 回解き、後処理で足した数などを 1 行で出す（httpx が要る）
- `python3 tools/try_phase1_settings.py` … 一段階目を重み・制限時間を変えて何通りか解く
